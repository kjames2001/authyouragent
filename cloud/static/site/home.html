The problem with agents today

An agent that books, buys or applies for you usually gets your password or a long-lived API key. Nobody can tell it apart from you, and nobody can limit it.

Without Auth Your Agent

  • The agent holds your password or a key that never expires.
  • The site sees "you", so it can't tell your actions from the agent's.
  • No limit on what the agent does once it is in.
  • Stopping it means changing your password everywhere.

With Auth Your Agent

  • The agent never sees your password. Its own key stays on its own machine.
  • The site sees the agent's name, the person it acts for, and the exact permissions.
  • Access covers only what you approved, for that one site, for as long as you chose.
  • Risky actions, like applying or paying, ask your phone again every time.
  • Revoke one site, or the whole agent, in one tap.

How an approval works

This is the real sequence the service runs, not a simplification. For the same errand told from each side, read how it works.

  1. The agent asks.It tells Auth Your Agent which site it wants and what it wants to do there.
  2. Your phone asks you.A notification shows the agent, the site and the permissions. You approve with your fingerprint or face (a passkey). Your password can approve basic access, but never a risky action.
  3. The agent gets a short-lived pass.It works for 10 minutes, for that one site, and only together with the agent's private key, so a stolen copy is useless on its own. The agent renews it by itself for as long as your approval lasts: until you revoke it, or the end you chose (1 hour to 30 days).
  4. The site checks every request.One call to our SDK confirms the pass, the key and that you haven't revoked it.
  5. Risky actions ask again.If the site marks an action as sensitive, your phone asks once more, and that approval can be used once only.

When the site has not adopted Auth Your Agent: the agent asks you to take over its browser. You sign in on your phone; the site sees a normal human login. When you are done, the agent continues on the logged-in page. Its browser runs in a vault on your machine, so it never holds your cookies, and it signs you out when its task is complete.

  1. The agent gets stuck.It reaches a login page, CAPTCHA, or 2FA prompt it cannot pass on its own.
  2. You get a notification.Your phone shows a live view of the agent's browser. You open it and take control; the agent is disconnected until you finish.
  3. You sign in yourself.You type the password, solve the CAPTCHA, enter the 2FA code. The website sees a normal human sign-in — no stored passwords, no cooperation required from the site.
  4. The agent gets its browser back.Once you have signed in, the browser is handed back automatically. The agent continues its task past the step that needed you. Anything that would submit, send, delete or pay asks your phone first.
  5. You are signed out when it is done.When the task is complete, the vault signs you out of each site, then destroys the browser profile. If it cannot sign out of a site, it tells you where to end that session. You can revoke the agent at any time from your phone.

Optional: saved sign-ins. If you keep agent logins in your own Bitwarden or Vaultwarden, the vault can type a saved password or authenticator code for the agent. The agent names the item; it never sees the value. Take over still handles everything else: CAPTCHAs, SMS or email codes, device approvals, passkeys, and sites you haven't saved.

  1. You choose what the agent can use.Only items in a folder named "Auth Your Agent" are visible, and the agent sees their names and sites, never the values. A separate account for agent logins is best.
  2. The vault checks the page first.A value is typed only on the address saved with the item, only in the page itself (not a frame), and only into the right kind of field: a password into a password field, a code into a code field.
  3. It fills, and keeps the secret to itself.The vault decrypts the item on your machine and types it in. The agent is told only that the field was filled, and the app shows which item it used on which site.

Guide for AI agents

Security, in plain terms

Details are in the security whitepaper.

Your fingerprint
Never leaves your phone. We receive a signed confirmation, not your biometric.
Agent keys
Generated on the agent's machine. We only ever see the public half.
Access passes
Signed tokens that expire in 10 minutes and are bound to the agent's key (DPoP, RFC 9449). New ones are issued only while your approval is still active.
Sensitive actions
Need a fresh approval every time, usable once, valid for 60 seconds.
Revocation
Takes effect on the next request for sites that check with us live, and within about a minute for sites that keep a signed revocation list locally.
History
Every approval, denial and revocation is written to a log you can read and export.

Agents report what breaks. We fix it.

When an agent uses Take over on a site and something does not work -- a login form hidden in shadow DOM, a bot challenge, a handback that does not trigger -- the agent's MCP server has a report_site tool that sends the site name and the issue to us automatically. The owner can see every report their agents file. We use them to improve site coverage. Nothing is hidden.

What gets reported
The site domain, the type of issue (shadow DOM, bot detection, missed input, failed takeover), and a one-line description. No credentials, no page content, no user data.
Who sees it
The agent's owner, in their dashboard. We see aggregated reports to prioritise fixes.
Why we do this
The web is messy. Shadow DOM, bot challenges and custom login flows change constantly. Agent-reported issues are the fastest way to find and fix real-world gaps.
